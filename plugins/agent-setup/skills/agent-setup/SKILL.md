# 프로젝트 에이전트 설정

설정은 두 층으로 다룬다. 두 층을 섞지 말고, 사용자에게 보여 줄 때도 어느 층인지 밝힌다.

1. **표준** — 각 에이전트의 공식 문서가 정한 구조. 폴더·파일·키 이름은 문서에 있는 것만 쓴다.
2. **특화** — 문서가 정하지 않은 부분에 대한 이 사용자의 선택. 아래 "특화 규칙"에 있는 것만 적용한다.

특화 규칙이 표준과 어긋나면 적용하지 말고, 어긋나는 점을 알리고 사용자에게 묻는다. 목록에 없는 것을 임의로 특화처럼 만들지 않는다.

## 표준을 확인하는 방법

기억이나 이전 프로젝트의 구성을 근거로 삼지 않는다. 매번 아래 순서로 확인한다.

1. **대상 에이전트를 정한다.** 프로젝트에 이미 있는 지침 파일·설정 폴더를 보고, 사용자에게 어떤 에이전트를 쓰는지 묻는다.
2. **에이전트마다 공식 문서를 찾는다.** 공식 문서를 탐색하는 스킬이나 도구가 있으면 그것을 쓴다. 없으면 직접 찾는다 — 제작사 문서 사이트의 색인(`llms.txt`, 사이트맵, 목차)에서 시작하고, 검색으로 찾았으면 제작사 공식 도메인인지 확인한다. 블로그·커뮤니티 글은 근거로 쓰지 않는다.
3. **아래 주제의 페이지를 읽는다.**
   - 지침 파일 — 이름, 탐색 순서, 다른 파일을 불러오는 방법, 여러 에이전트가 함께 읽는 공통 파일을 지원하는지
   - 설정 파일 — 위치, 범위(전역·프로젝트·개인), 프로젝트 설정이 적용되는 조건
   - 확장 — 스킬·명령·서브에이전트 같은 것을 두는 위치와 형식
   - 외부 도구 연결(MCP 등) — 등록 위치와 인증 방식
   - 버전 관리 — 문서가 커밋하라는 것과 제외하라는 것
4. **설치된 도구로 실제 동작을 확인한다.** 도구가 설정을 검증하거나 목록을 보여 주는 명령을 제공하면 그것으로 문서 내용이 이 버전에서 맞는지 본다.
5. **근거를 남긴다.** 보고할 때 항목마다 근거 문서 주소를 붙인다. 문서에서 확인하지 못한 것은 만들지 말고 "확인 못 함"으로 적는다.

여러 에이전트가 함께 쓸 수 있는 공통 규격이나 공유 방법을 문서가 지원하면 그쪽을 쓴다. 지원하지 않아 같은 것을 서로 다른 위치에서 읽어야 할 때만 각자의 표준 위치에 따로 둔다.

## 특화 규칙

- 지침 본문은 여러 에이전트가 함께 읽는 공통 파일 한 곳에 쓰고, 에이전트 전용 지침 파일에는 그 파일을 불러오는 한 줄만 둔다. (예: `CLAUDE.md` 에는 `@AGENTS.md` 한 줄만 둔다)
- 지침 문서에는 저장소를 읽으면 알 수 있는 내용을 쓰지 않는다. 파일만 봐서는 모르는 사실만 한 줄씩 적는다.
- 지침과 주석은 일반화해서 쓰기를 권장한다. 특정 서비스·도구·파일을 가리켜야 뜻이 통하는 곳에서는 이름을 그대로 쓴다.
- 외부에서 받는 확장은 본체를 커밋하지 않고 출처·버전을 기록한 잠금 파일만 커밋한다. 직접 만든 확장은 함께 커밋한다. (예: 직접 만든 프로젝트 전용 스킬은 `.gitignore` 에서 `!` 로 제외해 함께 커밋한다)
- 공통 설정과 특정 서비스 전용 설정은 커밋을 나눈다. 첫 커밋에는 공통 설정만 담는다.

사용자가 새 선호를 말하면 이 목록에 추가할지 묻는다. 추가할 때도 되도록 일반화한 문장으로 적고, 필요하면 예시로 구체적인 이름을 붙인다.

## 처음 만들 때

agent-scaffold 스킬을 쓴다. 뼈대를 스크립트로 만든 뒤, 커밋 전에 표준을 확인하고 특화 규칙을 적용한다.

## 기존 프로젝트를 정리할 때

1. 현재 설정 파일을 읽고, 표준을 확인한다.
2. 세 가지로 나눠 보고한다 — 표준과 어긋난 것, 특화 규칙이 적용되지 않은 것, 낡았거나 실제와 다른 내용.
3. 고칠 항목을 제안하고, 승인받은 것만 고친다. 표준에 맞는 기존 구성은 취향만으로 바꾸지 않는다.
